# Qwen 网络重试与 Task059 续跑

本次用户明确请求“优化 qwen 接口，允许多次进行重试，重新进行实验”，授权修复后重新尝试当前 UI-KOBE-like Task059。旧巡检中的禁止再次恢复约束不适用于这次明确授权的尝试；它仍适用于此后没有新授权的无限恢复。官方任务、素材、提示、GUI 编译与控制、评估保持原样。

原记录显示当前 episode 的步骤5在两个进程中分别两次连接失败，始终没有接受或执行步骤5。四个请求的 usage 均未知，不是已测量的零费用。原4条操作、失败分支和完整历史保持。此次从实际最新 safe4 检查点恢复同一 Docker VM，不重放原动作、不重置累计500限制。

改动仅影响 Qwen native 网络传输与显式运行配置：

- 最多6次实际请求（初始请求加5次重试），仍受原900秒请求与930秒步骤期限限制。Kimi 的两次重试上限不变。
- 对网络连接、读写、超时和远端协议断连，以及HTTP429/502/503/504进行有界重试。退避依次3、6、12、24、48秒；一般退避上限60秒，429仍按至少60秒与真实 Retry-After 等待。余额/配额、本地请求协议错误和完整候选的 schema 错误不走该网络循环。
- HTTPX 不保留空闲连接，降低复用被隧道关闭的连接的机会；这不保证上游服务恢复。
- 首次请求保留原最大16000输出上限。若失败 usage 未知，仍保守扣留该请求的完整预留输出；剩余请求按尚可用输出与剩余尝试次数分配。例如 actor 首次未知占16000后，剩余五次各最多3200，总预留不超过原32000。该分配是准入估计，不是实际费用。输入、语义修复次数和额外角色数量不增加。
- 所有请求使用不同 request ID，原 body、完整已知 usage、未知 NULL、错误与部分响应证据分别保留。只完整通过验证的候选才能到官方执行器。

新准备计划冻结 `qwen_transport_policy` 与 `stream_budget`，官方入口参数明确指定重试次数和退避上限。现存 checkpoint 只有显式传入 `--qwen-transport-attempts 6` 才迁移策略；产生新的 repair plan 与 continuation 目录，旧 plan/manifest/结果不覆盖。恢复器保存迁移前原 manifest，运行器严格比对计划、manifest 与命令行策略。

测试覆盖第五次断连后第六次成功、六次失败停止、完整未知记账、actor/advisory 输出池、连接新建、网络错误分类、配额立即停止、原期限截断，以及原参数和 UI-KOBE-like checkpoint/history 恢复。验证和 Ruff 在官方 Python 的注册128MiB、Swap0 scope 中串行运行。

新策略耗尽后仍须安全暂停，不能由30分钟巡检无限重启、探测或新建 episode。当前接口若仍不可用，保留 VM 和检查点并向用户报告；只有新的明确恢复/重试授权才能继续。只有原 native terminate 或累计500决策产生的原 official evaluation_result 才是评测成绩。
