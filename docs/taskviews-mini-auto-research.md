# TaskViews-mini 的 auto-research 迭代策略

状态：策略与开发测试方案；本文不启动循环、不恢复已暂停的 `osworld-20`，不自动重跑正式评测。依据是 [2026-10-16 三组复盘](taskviews-mini-keyboard-postmortem-20261016.md)。现有发票任务已用于诊断和改进，应归入开发集，不能再当未见测试集报告。

## 目标与不可混用的指标

目标是让 agent 在给定资源内形成正确操作、判断实际效果并完成任务交付，而不只是减少异常日志或让候选通过 parser。

| 层次 | 必记指标 | 不能推出的结论 |
|---|---|---|
| 生成 | 首候选合法键率、意图匹配率、错误命名空间率、修复次数 | 合法键不等于正确焦点 |
| 执行 | 实际键事件、指针位置、应用/控件状态变化、命令回执 | 回执0或像素变化不等于目标完成 |
| 记忆 | 正确主题送达率、有效操作检索命中、错误记录被仿写率、跨 episode 泄漏=0 | 多送历史不等于帮助决策 |
| 任务 | 原官方分数、终止声明、产物存在/位置、决策轮和 GUI 数 | 单任务单次结果不等于通用能力 |
| 成本 | 全部 API请求/重试、输入/输出/推理 usage、未知usage、时长、最低真实空闲内存 | 修复和失败请求不能从成本中删除 |

对键盘建立分层记忆：静态知识记录“目标意图、适用应用、焦点前提、确切 keys、知识来源”；episode 记录“原事件、使用的键、前后观察、控制器结果、模型效果判断”。模型效果判断属于可撤销声明，必须与观测和测试判据分列。只有明确的控件/内容变化判据通过后才能写入 `verified_effect`，不能用整屏 SHA 变化代替。

## 每轮研究单元

1. **取证**：从失败轨迹提取最早分歧和前置状态；保存事件/截图/源码 SHA。先判断接口、应用、焦点、定位、记忆还是规划问题。没有数据不填造原因。
2. **提出一个可证伪假设**：例如“加入意图到 backend 键名映射提高首候选正确率”，而不是“增加记忆会更聪明”。写清干预、对照、主要指标、失败条件、资源上限。
3. **先做最小模块回放**：已保存截图/动作测试 compiler、key spelling、scroll unit、焦点前提、对话框确认、文件移动和视图打包。保留已知成功 baseline 作为回归夹具，不向正式 actor 传入它的任务答案或未来动作。
4. **固定输入的生成对照**：同一截图、同一历史、同一 schema/模型/推理/输出上限，仅改一个视图因素；比较第一候选，不以“拦截后修复成功”冒充生成能力提升。给所有组相同意图约束的测试单独标为模块任务。
5. **受控 GUI 集成**：在新建、归属明确的测试环境中检查原动作真实触发事件及预期控件变化。独立保存旧/新实现结果，不能重放旧动作后把成功计为模型自主行为。若涉及 destructive 或外部效果，应改用本地可逆夹具。
6. **冻结候选后正式比较**：一次声明多个候选/种子/任务/成本总额，串行执行，完整保留所有失败。原评分器、任务文件、模型、坐标、硬资源和步数不随成绩调整。
7. **决定保留或回滚**：只按预先定义的指标选择，归档负结果与原因；实现变更、测试修复、环境故障分别记录。每个接受版本对应源码提交、配置、证据目录和变更说明。

## 第一批消融设计

| 候选 | 唯一主要干预 | 验证的问题 |
|---|---|---|
| C0 | 冻结 baseline 原生历史 | 原生生成参考 |
| C1 | 旧 Mini v2 | 原来的 proposals/attempts 提供了什么收益或负担 |
| C2 | 仅键名命名空间说明/映射，不加拦截 | 是否改善首候选键名 |
| C3 | C2＋独立按意图检索 keyboard view | 检索是否优于把全目录堆进 prompt |
| C4 | C3＋跨鼠标窗口的键盘 episode memory | 曾验证有效/无效操作能否被正确复用 |
| C5 | C4＋末端拦截 | 拦截带来的增益、额外调用和失败停止是否值得 |
| C6 | 对照替换 proposals 重复为交付进度/待确认事实 | 是否减少 UI-KOBE-like 式反复复核而不完成交付 |

本次代码是一个可用候选的组合实现，并非已经完成上述各项因果消融。后续用配置或独立提交切换因素，不能把不同预算、不同模型同时变化的结果解释成视图收益。

已完成的起点证据是2个保存现场×3个上下文的6次真实首候选测试：新 keyboard 上下文2/2正确，旧 Mini 和同历史无附加视图各0/2。它仅验证这些现场的键名生成，未评测语义效果或最终任务得分；逐例记录及输入哈希见[生成报告](../outputs/mini-keyboard-generation-20261016-v1/report.json)。下一轮应先拆分映射、检索和记忆的贡献，并补足重复采样与不同场景。

最优先的任务族：PDF 翻页/缩放、文件管理器创建/移动、表格导入/焦点输入、窗口切换。每族至少包含：正常状态、错误焦点、页面本来空白、模态对话框、非英文 UI、有效键但无可见内容变化。保留基于发票记录的开发夹具，同时新增未见内容和不同布局，防止只记住坐标、文件名或特定答案。

生成探针建议每个条件至少3次配对样本；少量样本报告逐例结果和区间，不凭两个成功案例宣称稳定改善。后续正式任务集的样本量、任务分层和停止规则在启动前确定。不能从评测集反复挑失败案例修复后仍把同一集合称为独立测试集。

## 按键感知与记忆的继续改进顺序

**P0：生成参考完整性。** 分开自然语言标签、X11 keysym、PyAutoGUI token、computer_use action enum；从冻结 backend 导出可用 token，并对每个 recipe 运行编译/事件测试。未知映射选择查阅视图或界面菜单，不能用大小写/下划线猜词规则。应用快捷键需标注应用、焦点和开关语义。

**P1：效果记忆。** 将“返回成功”和“目标变化”分开。对确定性夹具验证翻页后的页码/可见文字、缩放后的百分比、保存后的文件位置。将失败键和失败焦点分开索引；保留来源、时间、应用范围，切换 app 或窗口后降低复用信心。当前实现仅提供图像字节变化与原事件引用，尚未实现语义效果认证。

**P2：场景检索。** 目前采用最近意图和显式 `<key_lookup>`，下一步比较同 actor 的结构化场景描述、控件观察与应用提示。不要通过宿主机文件读取猜 guest 状态。明确选择器能否在正确时间送达视图、是否泄漏未来信息、输入预算不足时哪个视图被省略。

**P3：抑制错误自我强化。** 对重复模型计划去重，错误按键不作为可模仿 recipe；保留原始记录用于审计。事实/意图/尝试/确认四类分级。反复出现同一目标而无进展时提示重新检查单位、命名空间和焦点，不由硬编码策略替 agent 自动切换应用或执行答案。

**P4：交付进度。** 记录任务要求的产物、已观察证据、仍待执行的动作和未确认结果。出现矛盾才重读已解决信息；对“输入名称”“确认创建”“移动文件”“验证位置”分开。每个状态更新必须绑定本 episode 的观察，不从 evaluator/gold 借用任务解法。

## 预算与停止条件

未来批次若沿用当前比较，仍固定 qwen3.8-max/high、SX_URL_SB、每组40决策、原图/历史/输出预算。Windows 真实空闲 RAM 必须大于2 GiB；本项目占用另记，不重复扣也不抵消低空闲；VM3GiB、actor2GiB、辅助128MiB、零swap，C/D磁盘45/12GiB。需要变更时建立新的实验规格，不覆盖旧记录。

研究控制器应只允许修改 Mini/视图/测试/文档白名单，禁止修改任务、评分器、测试集答案、旧轨迹或资源规则。模型调用总量、总输出和费用上限必须在每批授权中具体填写，未填写不启动自动循环；一次批次授权后无需每个可逆迭代重复确认。遇配额、持续网络故障、OOM、源码漂移、数据泄漏、不可解释评分或清理失败即停止并保存证据；无有效官方 result 时分数为 null。

建议每批最多3个代码候选，每个候选最多2轮修复基础测试；未过回放不调用正式评测。仅对代码修复重新做受影响检查，不能为了成绩重复运行。20分钟巡检只检查阶段变化/失败/完成，不参与策略调度或补跑。

## 机器可读实验记录

每个 iteration 写一份不可覆盖 manifest：`iteration_id / parent_commit / hypothesis / changed_factors / source_sha256 / input_case_ids / split / model / endpoint_env / reasoning / budgets / max_trials / stopping_rule / primary_metric / acceptance_rule`。结果分别写 `generation.jsonl / execution.jsonl / memory_audit.json / official_outcome.json / usage.json / resource.json / decision.md`。

记录中标明 `recorded_response_replay`、`live_generation_only`、`gui_module_test` 或 `formal_evaluation`；首候选、修复候选、真实执行和最终分数分别计数。接受版本必须通过：无泄漏、关键历史/检查点不丢、成功轨迹编译一致、真实键/滚轮语义一致、原预算有效、原评分可复核。无法满足任一项则保留负结果并回滚候选。
